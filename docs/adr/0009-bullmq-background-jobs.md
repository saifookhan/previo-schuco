# 0009 — BullMQ (Redis) for background job processing

## Status

Proposed

**Author:** Syed Arif Iqbal (arifiqbal@outlook.com)
**Date:** 2026-09-04

## Context

Several already-planned features are time-consuming or CPU-intensive enough that they must not run inline in an HTTP request/response cycle on `apps/api`: sending invite/notification emails ([0004](./0004-admin-invite-only-onboarding.md) currently relies on Cognito's own built-in invite email, but future transactional email — password reset reminders, quote-status notifications — will not all route through Cognito), PDF generation for quotes/invoices (`docs/project-context.md` Phase 4 — "Documents & I/O"), and bulk import/export (Phase 4) and reporting jobs (Phase 5 — "Platform services"). `apps/api` is a request/response BFF (Hono on ECS Fargate); it has no queue, no worker, no scheduled/retryable job primitive today.

`docs/architecture.md` already sketches an async story — **"Async (Phase 5+): SQS for reports, notifications, bulk import"** — written before this decision. This ADR **supersedes that line**: the platform will use **BullMQ (Redis-backed)** instead of SQS for background job processing. `docs/architecture.md` is updated alongside this ADR to reflect it.

**Why BullMQ over SQS**, given both are legitimate choices for a small team:
- Redis is already a first-class, planned dependency of this stack — [0005](./0005-env-target-composition.md) already reserves `REDIS_TARGET`/`REDIS_URL_*` in the env-composition design specifically anticipating "a future service (a queue broker)." Adopting BullMQ cashes in that design rather than introducing a second, unrelated async substrate (SQS) alongside it.
- BullMQ gives delayed jobs, repeatable/scheduled jobs, retries with backoff, priorities, rate limiting, and job-state introspection (Bull Board) as first-class, code-level primitives with a Node-native API — SQS provides the queue transport only; the same features (delay, retry policy, DLQ, visibility) require assembling multiple AWS primitives (SQS + Lambda or ECS consumers + DLQ + EventBridge for scheduling) and are harder to exercise identically in local dev without AWS access.
- Team size and current infra maturity (single ECS cluster per environment, no existing Lambda/EventBridge usage anywhere in `infra/terraform/`) favor one more per-environment resource (a small ElastiCache Redis, or local Docker Redis) over standing up a second AWS-native async architecture from scratch.
- Trade-off accepted: BullMQ requires running and operating a Redis instance per environment (availability, memory sizing, eviction policy — must be an eviction-disabled/`noeviction` policy for queue correctness, unlike a cache-shaped Redis), whereas SQS is fully managed. This is judged worth it for the DX and feature gains above, at current scale.

## Decision

1. **New workspace package `packages/queue`** (library-first, per `docs/architecture.md`'s "Libraries first" principle — not a separate deployable until scale requires it). It owns:
   - A Redis connection factory reading the already-resolved `REDIS_URL` (via `packages/env`, [0005](./0005-env-target-composition.md) — no new env mechanism).
   - A typed `defineJob(name, payloadSchema, handler)` helper: every job type declares a Zod payload schema up front (mirroring how `packages/contracts` defines request/response schemas) and an `enqueue<JobName>(payload)` function — route handlers and other callers never call raw BullMQ `Queue.add()` with an untyped payload.
   - **One BullMQ Queue per job domain**, not per individual job type: `email`, `documents` (PDF/render), `import-export`. Each domain gets its own concurrency and rate-limit tuning (e.g. `documents` capped low since PDF rendering is CPU-heavy; `email` can run higher concurrency). Job *types* within a domain are BullMQ job `name`s on that queue (e.g. `email` queue carries `invite-email`, `quote-status-email` job names).

2. **Every job declares an explicit execution scope — `tenant` or `platform` — as part of the job's type, not as a boolean flag inside an otherwise-uniform payload.** There is no HTTP request to inherit tenant context from in a worker process, so scope cannot be implicit or inferred from payload shape:
   - A **tenant-scoped** job's payload always carries `companyId`; the worker runs its DB work via `withRlsTransaction(db, { companyId: job.data.companyId, isSuperAdmin: false }, ...)` ([0006](./0006-rls-request-scoped-transaction.md)) — reusing the exact mechanism `requireAuth` uses, not a parallel one.
   - A **platform-scoped** job (genuinely cross-tenant — e.g. a nightly digest) is a distinct job *kind* declared as such at definition time, not a tenant job with `isSuperAdmin: true` slipped into its payload. The job-definition helper distinguishes the two up front (e.g. a `scope: 'tenant' | 'platform'` on the definition itself), so it's the worker's dispatch logic — not the job author's payload — that decides which DB access mode a given job *name* is allowed to use. This closes off the accidental-privilege-escalation shape of `{ companyId: <anything>, isSuperAdmin: true }` appearing in data a bug or a compromised enqueue call could construct: scope is fixed by the job type's declaration, never by caller-supplied data.
   - This mirrors the same discipline [0002](./0002-cognito-identity-only.md) and [0006](./0006-rls-request-scoped-transaction.md) already apply to request handling — elevated access is a property of a reviewed, named code path, never an ambient flag a payload can set.

3. **Delivery guarantee — stated precisely, not oversold.** BullMQ (like essentially every queue system without a two-phase-commit into the side effect itself) provides **at-least-once execution, not exactly-once**. Deterministic `jobId` (e.g. `invite-email:${invitationId}` — keyed to the invitation, not the user, so a legitimate resend of an invite isn't blocked by dedup against the original send; see the job-ID-choice note below) prevents a *duplicate enqueue* of the same logical job while one with that id is still pending/active in the queue — it does **not** prevent a job's *handler* from running twice. The concrete failure this matters for: a worker sends an email successfully, then crashes (or the process is killed, or the connection drops) before it acknowledges the job as complete; BullMQ correctly treats the job as not-yet-done and retries it; the handler runs again and sends the email a second time. `jobId` dedup does nothing to stop this, because it's the same job being retried, not a second job being enqueued.
   - **Rule**: every job handler must be written assuming at-least-once execution and must be idempotent on retry.
   - For jobs where a duplicate side effect is merely wasteful (e.g. regenerating a PDF that gets overwritten either way), idempotent-by-nature is enough — no extra bookkeeping needed.
   - For jobs where a duplicate side effect is user-visible and undesirable (sending the same email twice is the canonical case), the handler should check-and-record via an application-level delivery ledger (e.g. an `email_delivery` table with a `UNIQUE` constraint on a business key like `(invitation_id)`) before attempting the external call — insert-or-detect-existing, then send, so a retried handler that finds an existing "sent" record skips the external call.
   - **This reduces the duplicate-send window; it does not eliminate it, and the ADR should not claim otherwise.** The ledger write and the external send are not one atomic operation — Postgres and an external email provider don't share a transaction — so a crash between "the provider accepted the send" and "the ledger records it" still produces a duplicate on retry. **The honest guarantee this system provides is: at-least-once job execution, with application-level idempotency that reduces but cannot guarantee zero-duplicate external delivery.** If a specific job's business requirement is genuinely zero-duplicate delivery, that needs either an idempotency key supported by the external provider itself (many transactional email APIs offer one) or a transactional-outbox pattern — neither is adopted platform-wide here; it's a per-job decision made if and when a job's actual requirements demand it, not built pre-emptively for job types that don't exist yet.
   - **Job-ID choice matters beyond dedup mechanics**: keying `jobId` to a business identifier that can legitimately recur (a user ID, for "send this user an email" generically) risks a *correct* second send being silently swallowed by dedup against a stale first attempt. Key `jobId` to the specific event/attempt the job represents (an invitation ID, a specific notification instance), not to a long-lived entity that can validly trigger the same job type more than once over its lifetime.

4. **Operational failure semantics — decided now, not left implicit**, since "we'll figure it out" is how silent job loss happens in production:
   - **Retry policy**: bounded retry count with exponential backoff per job domain (exact numbers are tuning, not architecture — but "unbounded retries" and "no backoff" are both explicitly rejected as defaults).
   - **Timeouts at two levels, not one**: every job type declares a max execution time for the job as a whole, treating a job that exceeds it as failed (triggering retry/backoff) rather than left to run indefinitely and hold a worker slot — *and*, separately, every external I/O call a handler makes (an HTTP call to an email provider, a Cognito call, a PDF-rendering subprocess) has its own bounded timeout. A job-level timeout alone doesn't help if the handler is blocked inside a hung external call with no timeout of its own — the job-level timeout only fires once that call eventually resolves (or never, if it hangs forever). Rule: every job, and every external I/O operation inside its handler, must have an explicit bounded timeout.
   - **Failed-job handling**: after retries are exhausted, a job moves to BullMQ's failed state and stays there (bounded retention, not deleted immediately) — a permanently-failed job must be visible (via Bull Board or equivalent) and, for anything tied to a user-facing action (the invite-email case, per [0004](./0004-admin-invite-only-onboarding.md)'s reconciliation strategy), reflected back into the owning domain's own state (e.g. `users.status = 'invite_failed'`), not left as a fact only Redis knows about.
   - **Completed/failed job retention**: bounded (BullMQ's `removeOnComplete`/`removeOnFail` age/count limits), so Redis memory doesn't grow unbounded from job history — exact limits are tuning, but "unbounded retention" is rejected as a default.
   - **Worker concurrency**: set per queue (per job domain), not globally — CPU-heavy domains (`documents`) get a low concurrency ceiling, I/O-bound domains (`email`) can run higher.
   - **Graceful shutdown**: the worker process must stop accepting new jobs and let in-flight jobs finish (within their timeout) before exiting on a deploy/restart signal — an ungraceful kill mid-job is exactly the crash-before-ack scenario in point 3 above, so minimizing how often it happens (vs. relying solely on idempotency to paper over it) matters operationally.
   - **Redis persistence**: the per-environment Redis must persist queue state across restarts (AOF, or RDB with an acceptable data-loss window) — a queue backed by a Redis with no persistence silently loses any job that was only in memory when Redis restarted, which is a correctness gap, not just an availability one.

5. **Deployment**: the worker runs as its **own process, its own ECS service and task per environment** — never a second process inside the API's request-handling task — so a slow/stuck job (e.g. PDF rendering) cannot starve HTTP request handling, and the worker scales independently of API traffic. Per [0003](./0003-per-environment-isolation.md), each environment's worker connects only to that environment's own Redis and RDS — no shared queue infra across dev/staging/prod. It may ship from the same Docker image as the API to avoid a duplicate build/dependency surface — that and the exact entrypoint mechanism are implementation detail.

6. **Infra**: Redis is provisioned per environment, isolated per [0003](./0003-per-environment-isolation.md) — never shared across dev/staging/prod. It must run with **eviction disabled** (a full Redis must fail job enqueue loudly, never silently drop queued jobs to make room) and **persistence enabled** (per point 4's Redis-persistence requirement). Exact image/version, hosting mechanism (local Docker vs. a managed service), sizing, and Terraform module layout are implementation detail, not fixed by this ADR — they can change without a revision here as long as the two invariants above (no eviction, persistence on) hold.

## Consequences

- `docs/architecture.md`'s "Async (Phase 5+): SQS for reports, notifications, bulk import" line is superseded by this ADR and updated to reference BullMQ/Redis instead.
- Redis becomes a **required**, not optional, per-environment dependency the moment the first job type ships, with a stricter persistence/eviction configuration than a typical cache-shaped Redis would need.
- A new operational surface exists: Redis must be monitored/sized (queue depth, memory, persistence lag), and the worker ECS service needs its own health/restart policy and graceful-shutdown behavior, separate from the API's.
- Every future job type is reviewed against two standing rules: (a) explicit `tenant`/`platform` scope declared at the job's definition, never an `isSuperAdmin` flag inferred from payload data (point 2), and (b) idempotent-on-retry, with an honest statement of what its dedup guarantee actually is rather than an assumed "jobId fixes it" (point 3) — the same way [0006](./0006-rls-request-scoped-transaction.md) already flags `getDb()` vs `withTenantDb` misuse in routes.
- Local dev gains a Redis dependency for anyone working on a feature that enqueues jobs.
- **This ADR fixes architectural invariants, not implementation specifics.** Exact package/file names, Redis image tags, Terraform module paths, BullMQ option identifiers, and similar concrete choices are expected to evolve independently over time; only the rules stated in the Decision section above (BullMQ over SQS, one queue per domain, explicit tenant/platform scope, at-least-once + idempotent handlers with an honestly-stated dedup guarantee, bounded retries/timeouts/retention, worker as its own service, Redis isolated/no-eviction/persistent) are binding without a new ADR.
